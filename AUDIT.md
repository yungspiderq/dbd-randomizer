# Аудит исходного скрипта DBD Universal Randomizer (v1 → v2)

Проверено: 29.09.2026. Релевантный патч игры: **10.1.2a** (44 убийцы, 54 выживших).
Все пункты — про ваш исходный файл. «v2» = `dbd_randomizer.py` в этой папке.

Легенда: 🔴 критично (ломает работу/вешает), 🟠 существенно (портает результат), 🟡 мелочь/UX.

---

## A. Потоки и стабильность

### A1 🔴 Tkinter дёргается из рабочего потока
```python
threading.Thread(target=self.run_full_automation, daemon=True).start()
...
self.status.config(text="...")        # из потока!
self.btn_generate.config(state=tk.DISABLED)
messagebox.showerror("Ошибка кликера", str(err))
```
Tk-interpreter не потокобезопасен: обращение к виджетам не из главного потока даёт
случайные `RuntimeError`, «подвисшие» надписи или краш процесса (на CPython обычно
«просто работает», но это гонка — падает в самый неподходящий момент, во время кликов).

**v2:** весь поток только складывает сообщения в `queue.Queue`, главный поток разбирает
очередь через `root.after(70, ...)` (`_poll_ui_queue`). Кнопки включаются через `root.after(0, ...)`.
`messagebox` из потока больше не вызывается.

### A2 🔴 Окно захвата координат может уничтожить сборщик мусора
```python
def grab_coordinates(self, key):
    grabber = CoordinateGrabber(self.root)     # локальная переменная
    self.root.wait_window(grabber.top)
```
После возврата из `grab_coordinates` на `grabber` нет ссылок → CPython может собрать
объект, а `Toplevel` при этом закрывается/«отваливается» (классический баг Tkinter).
Проявляется как «иногда окно захвата исчезает само» или «координаты не записываются».

**v2:** `self._grabber = CoordinateGrabber(...)` + сброс в `None` после `wait_window`.

### A3 🟠 Координата записывается по любому клику в окне, включая заголовок/крестик
`self.top.bind("<Button-1>", self.on_click)` ловит и клик по кнопке закрытия.

**v2:** отдельная обработка, live-показ `x/y` под курсором, `Esc` — отмена (координата не пишется).

### A4 🔴 Нет способа прервать автоматизацию
После старта мышь «угнана» на 10–20 секунд; если открылось не то окно — клики уйдут в систему.
Единственный аварийный выход — `pyautogui.FAILSAFE` (мышь в левый верхний угол), о котором в UI ни слова.

**v2:** глобальная горячая клавиша СТОП (`keyboard`, по умолчанию **F9**, настраивается),
кнопка «⏹ СТОП» в UI, прерываемый `sleep`, отменяемый обратный отсчёт, FAILSAFE остаётся.

### A5 🟡 `pyautogui.PAUSE = 0.05` — мёртвый код
Все клики идут через `pydirectinput`, у которого свой `PAUSE`.

**v2:** оба PAUSE выставлены явно (0), задержки управляются настройками таймингов.

## B. Автоматизация (клики/поиск)

### B1 🔴 0.01 с на фильтрацию выдачи — поиск не успевает
```python
self.safe_paste(target_name)
time.sleep(0.01)      # «минимальное ожидание фильтрации»
self.dbd_click(first_res)
```
Клиент DBD перерисовывает список за ~100–400 мс (зависит от диска/кэша). Клик по
`first_result` через 10 мс попадает **по предыдущей выдаче** — экипируется прошлый
предмет/перк. Это главная причина «ставит не то».

**v2:** `search_settle` = 0.35 с по умолчанию (настраивается 0.1–2 с), повторные попытки
с увеличенной паузой, опциональная OCR-проверка имени результата перед кликом.

### B2 🟠 Клик по «×» очистки, когда поле пустое
Кнопка очистки в DBD появляется только при непустом поиске. Клик по её координате при
пустом поле уходит в случайный элемент интерфейса.

**v2:** по умолчанию поле чистится `Ctrl+A` (работает всегда), клик по «×» — отдельная
галка «Кликать кнопку очистки».

### B3 🟠 Вставка из буфера без проверки
```python
pyperclip.copy(text); time.sleep(0.02); pydirectinput.press('v')
```
`pyperclip.copy` на Windows может не успеть/упасть при занятом буфере → вставится
**старый** текст (остаток от предыдущего шага) → экипируется не то. Плюс ваш буфер обмена затирается.

**v2:** цикл подтверждения (`paste() == text`, до 6 попыток), опция восстановления
прежнего содержимого буфера, предупреждение в логе, если подтвердить не удалось.

### B4 🟠 Если поиск ничего не нашёл — клик всё равно происходит
Пустая выдача не проверялась: клик по координате `first_result` в пустом списке может
нажать на что угодно (или на «подсвеченный» результат прошлого поиска).

**v2:** опциональный OCR (`pytesseract` + область экрана) — при несовпадении имени клик
**пропускается**, пишется предупреждение; без OCR — повторы поиска с удлинённой паузой.

### B5 🟠 Имена-префиксы: «Фонарик» ⊂ «Маскарадный фонарик»
Поиск DBD — подстрочный, поэтому по запросу «Фонарик» первой иконкой может оказаться
«Спортивный фонарик», «Аптечка» → «Аптечка годовщины» и т.п. (валидатор v2 нашёл 20+ таких пар).

**v2:** параметр `result_index` (какую иконку выдачи брать, 1–9) + `result_step` (шаг сетки
в пикселях) + OCR-проверка. Валидатор базы печатает все конфликтные пары.

### B6 🟡 Клики «в ноль» и мгновенный прыжок курсора
`mouseDown → 0.03 → mouseUp` иногда не регистрируется игрой; `moveTo` одним прыжком
в полноэкранном режиме бывает игнорируется.

**v2:** `hold` = 0.06 с по умолчанию, перемещение в N шагов (`move_steps`), все значения в настройках.

### B7 🟡 Нет DPI-awareness
Без `SetProcessDpiAwareness` при масштабе Windows 125/150 % координаты, снятые в
Tkinter, и координаты игры расходятся — клики «уезжают».

**v2:** DPI-awareness выставляется до создания окон; захват координат берёт
`winfo_pointerxy()` (физические пиксели), с fallback на `pyautogui.position()`.

### B8 🟡 Требовались все 10 координат сразу, даже когда часть не нужна
В режиме МАНЬЯК слот предмета не используется, «×» очистки — опционален. Из-за этого
запуск блокировался с сообщением про ненужную координату.

**v2:** список обязательных координат строится из фактических шагов билда; сообщение
перечисляет все недостающие сразу и открывает нужную вкладку.

### B9 🟡 Не было «сухого прогона»
Проверить порядок действий без игры было нельзя.

**v2:** галка «Сухой прогон» — лог всех кликов/вставок без единого реального действия
(работает даже не под Windows).

## C. Данные игры

### C1 🔴 Два противоречащих списка навыков убийц
`ALL_KILLER_PERKS` (используется) и `KILLER_PERKS` (мёртвый код) описывают одно и то же
**по-разному**, и оба содержат несуществующие/неточные названия:

| ALL_KILLER_PERKS | KILLER_PERKS | комментарий |
|---|---|---|
| Поиграть со своей **жертвой** | Поиграть со своей **едой** | разные переводы одного перка |
| Тактика **зансин** | Тактика **зловещего** | EN: Zanshin Tactics |
| Секущий крюк: **секрет палача** | **Трюк палача** | EN: Scourge Hook: Gift of Pain |
| **Детище тьмы** | **Теневой рожденный** | EN: Shadowborn |
| Фанатение | Рикошет звезд | EN: Starstruck |
| Соленое море / Безжалостный шторм | Звонок из могилы / Морская буря / Проклятие Садако | Онрё |
| — | Клаустрофобия (у Клоуна) | EN Claustrophobia — перк Джефф, у Клоуна его нет |

Любое расхождение с реальным именем в игре = поиск ничего не находит (см. B4).

**v2:** один источник истины — `killers[*].perks` (3 своих) + `killer_common_perks`.
Спорные записи помечены `⚠ ПРОВЕРИТЬ`, валидатор подсвечивает подозрительные формы.

### C2 🔴 Нет нового убийцы и нового выжившего (патч 10.1.0, 25.08.2026)
«Хор греха» добавил **Судью** (EN The Judgment, сила Will of the Gods, перки
Celestial Witness / Hex: Under Your Thumb / Lay Waste) и выжившую **Аврору**
(Fruits of your Labor / Salvation's Cry / Boon: Steadfast). В вашей базе 43 убийцы и 53 выживших.

**v2:** 44 убийцы и 54 выживших; у Судьи пустой список аддонов (RU-названия ещё не
опубликованы) — автоэкипировка корректно пропустит шаг. Русские имена новых перков
помечены как требующие проверки (фан-вики использует вариант «Правосудие»).

### C3 🟠 Несовпадение ключей между словарями
- `KILLERS_DATABASE["Хороший Парень"]` vs `KILLER_PERKS["Хороший Парень"]` vs `ALL_KILLER_PERKS` → «Хороший **п**арень»;
- `KILLERS_DATABASE["Тёмный Властелин"]` (Тёмный **В**ластелин) vs `KILLER_PERKS["Темный Властелин"]`;
- «Тёмная преданность» / "Темная преданность", «Мёртвая хватка» / «Мертвая хватка» — ё/е вперемешку.

Поиск в DBD нечувствителен к регистру, но **чувствителен к ё/е и к опечаткам** — а словарь
в коде при расхождении ключей просто молча отдаёт не то.

**v2:** ключи нормализованы, валидатор сравнивает имена с нормализацией (регистр + ё→е)
и сообщает о коллизиях.

### C4 🟠 Сила Ксеноморфа = «Скрытная погоня» — совпадает с перком Гоуст Фейса
EN сила Ксеноморфа — *Hidden Pursuit*, а «Скрытная погоня» у вас же стоит в навыках
Гоуст Фейса. Как минимум одно из двух не совпадает с игрой.

**v2:** запись помечена `⚠ ПРОВЕРИТЬ` (на экипировку не влияет: сила убийцы не
экипируется, но в выдаче поиска перков такое имя может мешать).

### C5 🟠 Режим МАНЬЯК брал перки «из всех сразу»
```python
perk_pool = ALL_KILLER_PERKS + KILLER_COMMON_PERKS
self.current_generated_perks = random.sample(perk_pool, 4)
```
Выбранному убийце доставались любые перки всех убийц — включая те, что не открыты
(нет престижа/храма). Автоэкипировка в таком случае тыкает в пустую выдачу.

**v2:** три режима — «общие» (есть у всех), «уникальные» (3 своих + 1 общий),
«смешанные»; плюс белые списки `OWNED_*` в JSON: если включён режим
«только открытое у меня», недостающие слоты остаются пустыми и **не кликаются**.

### C6 🟠 Режим ВЫЖИВШИЙ брал перки всех отмеченных персонажей
```python
for surv in available_survs: all_unique_perks.extend(SURVIVOR_PERKS.get(surv, []))
```
Выпавший персонаж получал чужие уникальные перки (у себя в кровавой паутине их нет),
а `SURV_COMMON_PERKS` не фильтровался по факту открытия.

**v2:** пул = перки выпавшего персонажа + общие, с учётом белого списка.

### C7 🟡 `random.sample(perk_pool, 4)` без защиты
Если пул < 4 (например, отметили одного персонажа в режиме «уникальные», или
в списке всего 3 перка) — `ValueError: Sample larger than population`, окно падает.

**v2:** `_pick()` + `_fill_perks()` — никогда не бросает исключение, добирает слоты
из запасных пулов или оставляет их пустыми.

### C8 🟡 Названия категорий предметов не используются
`chosen_category` вычислялась и показывалась в подписи, но в поиск не передавалась —
при совпадении имён (B5) не было страховки.

**v2:** категория показывается в билде, а для точности добавлены `result_index`/OCR.

### C9 🟡 Аддоны без учёта редкости
Случайная пара аддонов часто получается нелегальной по редкости (в DBD два
«ультра-редких» одновременно поставить нельзя) — игра такие не примет.

**v2:** структура данных готова под редкости (можно добавить поле `rarity` в JSON),
пока — честное предупреждение в README; при отказе игры аддон просто не встанет.

## D. Конфигурация и UI

### D1 🟠 Файл конфига привязан к рабочей директории
```python
CONFIG_FILE = "dbd_randomizer_config.txt"
```
Запуск ярлыком/из другой папки → настройки «теряются» (создаётся новый файл в CWD).

**v2:** путь от `__file__`; JSON вместо txt; атомарная запись (`tmp` + `os.replace`);
битый файл переименовывается в `.broken`, старый txt мигрируется автоматически.

### D2 🟠 Разбор конфига чувствителен к пробелам
`key, val = line.strip().split("=", 1)` — строка `search_x = 100` даёт ключ `"search_x "`
(с пробелом) → значение молча теряется.

**v2:** JSON, ключи дополнительно нормализуются при миграции.

### D3 🟠 «Никого не выбрал» и «выбрал всех» неразличимы
```python
is_owned = True if not self.config.get("owned_killers") else (k_name in saved_killers)
```
Сняли все галки → сохранили пустую строку → при следующем запуске снова отмечены все.

**v2:** хранится список в JSON (`owned.killers`), пустой список означает «никого»
и валидируется перед генерацией (в v1 пустой список тоже ловился, но только до сохранения).

### D4 🟡 Нет автосохранения при закрытии
Закрыли окно, не нажав «Сохранить» — отметки персонажей потеряны.

**v2:** `WM_DELETE_WINDOW` сохраняет отметки и настройки; отдельная кнопка тоже осталась.

### D5 🟡 Окно 620×860 с фиксированной раскладкой
Кнопка «Сохранить координаты» при `pack` после растянутого canvas уезжала за границу
окна; `minsize` не задан; часть чекбоксов не видна.

**v2:** grid + `minsize(900, 620)`, вкладки масштабируются, панели на `Panedwindow`.

### D6 🟡 Списки не прокручиваются колесом и обрезаются по ширине
У `Canvas` не было `bind("<MouseWheel>")` и привязки ширины внутреннего фрейма.

**v2:** колесо мыши (Windows + X11-кнопки 4/5), ширина контента = ширина canvas.

### D7 🟡 `ttk.Style` с темой `default` на Windows игнорирует цвета
Тёмная тема применялась частично (классические ttk-виджеты оставались серыми).

**v2:** тема `clam` + явные стили для всех виджетов, `tk.Checkbutton/Radiobutton`
там, где нужен настоящий тёмный фон.

### D8 🟡 Не было фильтра по имени персонажа и кнопок «все/никто/инверсия»
100+ чекбоксов листать вручную.

**v2:** фильтр, три кнопки массового выбора, сохранение списка.

### D9 🟡 Не было журнала и проверки данных
Ошибки автоматизации видно не было — только статусная строка на 1 строку.

**v2:** журнал с таймстампами, кнопка «🩺 Проверить базу» (отчёт + `dbd_data_report.txt`),
«📝 Открыть dbd_database.json», «🔄 Пересоздать базу», «🧪 Тестовый клик».

## E. Зависимости и запуск

### E1 🟠 `import pyautogui, pydirectinput` на верхнем уровне
`pydirectinput` падает на импорте вне Windows (`ctypes.windll`), `pyautogui` — без DISPLAY.
Скрипт нельзя даже открыть на второй машине/в CI, чтобы поправить базу.

**v2:** импорт спрятан в класс-обёртку; GUI и логика работают без них, а автоматизация
сообщает внятную причину и предлагает «сухой прогон».

### E2 🟡 Горячая клавиша СТОП требует `keyboard`
**v2:** `pip install keyboard` (опционально, но настоятельно рекомендуется);
если библиотеки нет — остаются кнопка СТОП в окне и FAILSAFE мышью.

## Что осталось сделать вам руками (5 минут)

1. `pip install pyautogui pydirectinput pyperclip keyboard`
2. Запустить, на вкладке **ПЕРСОНАЖИ** отметить реально открытое → Сохранить.
3. На вкладке **КЛИКИ И ТАЙМИНГИ** снять координаты (кнопка «🎯 Клик» на каждом поле).
4. Открыть `dbd_database.json` и сверить с игрой записи, помеченные в README `⚠`:
   Судья (имя/сила/перки/аддоны), Аврора, «Сейбл/Сэйбл Уорд», «Егерь/Псарь»,
   сила Ксеноморфа, перки Неведомого.
5. Первый прогон — с галкой **«Сухой прогон»**: посмотрите журнал, убедитесь,
   что порядок шагов и имена правильные. Затем снимите галку.
6. Если поиск часто берёт не ту иконку — поставьте `result_index` = 2/3 или включите
   OCR (нужен Tesseract с русским языком: `pip install pytesseract` + установщик tesseract-ocr).

# F. Дополнительно найдено в актуальной версии репозитория (v1.1.1)

Пункты A–E описывают файл, присланный в чат. Репозиторий `yungspiderq/dbd-randomizer`
содержит более развитую v1.1.1 (1842 строки): билды сообщества, автообновление,
упаковка в пакет. Все баги из разделов A–E в ней **живы** (проверено построчно:
`grabber = CoordinateGrabber(...)` — строка 1263, `CONFIG_FILE` относительно CWD — 989,
`time.sleep(0.01)` перед кликом по выдаче — 1776, `random.sample(perk_pool, 4)` — 1692 и 1723,
`self.status.config(...)` из потока — 1785+). Плюс нашлось новое.

### F1 🔴 Автообновление = удалённое выполнение кода у всех пользователей
```python
def update_files_in_place():
    path = os.path.abspath(__file__)
    content, _ = _get_remote_file_b64("dbd_randomizer.py")   # ref=main
    if not content or len(content) < 1000: return False
    os.replace(tmp, path)                                     # перезапись самой себя
```
Файл берётся из **ветки main**, проверка — только «длина больше 1000 байт», после чего
программа перезаписывает собственный исходник и перезапускается (`restart_app`). Любой,
получивший право записи в репозиторий (утёкший токен, угнанный аккаунт, принятый
вредоносный PR), мгновенно рассылает свой код всем пользователям. В HTML-страницу
или пустой файл проверка тоже пропустит всё, что длиннее килобайта.

**v2:** загрузка из **тега релиза**; скачиваются все модули во временные файлы и
проверяются (размер + обязательный маркер + `compile()` на синтаксис) **до** записи;
пользователю показываются размер и SHA-256 каждого файла; старые версии остаются в `.bak`;
конфиг и токен не перезаписываются; «Позже» запоминает версию и больше её не предлагает.

### F2 🔴 `.gitignore` склеен — конфиг с токеном не игнорируется
```
__pycache__/dbd_randomizer_config.txt      <- строка 1: два паттерна слиплись в один
community_builds_cache.json
__pycache__/
```
Первая строка — результат неудачного мержа: вместо `__pycache__/` и
`dbd_randomizer_config.txt` получился один несуществующий путь. Значит
**`dbd_randomizer_config.txt` НЕ игнорируется**, а в него `save_build_settings()` пишет
`gh_token=...` (`save_config` сохраняет весь словарь). Пользователь, который делает
`git add .` в папке программы, публикует свой токен вместе с конфигом.

**v2:** `.gitignore` переписан; игнорируются `dbd_randomizer_config.json`,
`dbd_randomizer_config.txt`, `.github_token`, `dbd_database.json`,
`community_builds_cache.json`, `*.bak`, `*.new`. Проверено `git check-ignore -v`.

### F3 🟠 Токен пользователя лежит в конфиге открытым текстом
`gh_token` пишется в тот же файл, что и координаты, и читается `get_saved_token()` в том
числе для автообновления — то есть токен с правом записи используется и там, где достаточно
чтения. Плюс он подставляется в заголовки запросов при каждой проверке обновлений.

**v2:** хранение осталось (иначе фича неработоспособна), но токен больше не участвует в
обновлении без явной необходимости, в README добавлено предупреждение, а `.gitignore`
гарантирует, что файл не уедет в репозиторий. Дальнейшее улучшение — хранить токен через
`keyring` (Windows Credential Manager), а не в тексте.

### F4 🟠 `publish_build_to_github` теряет данные при повреждённом JSON
```python
builds = json.loads(base64.b64decode(data["content"]).decode("utf-8"))
```
Если общий файл окажется битым, `json.loads` бросит исключение **до** ветки `except
urllib.error.HTTPError` — публикация упадёт с невнятной ошибкой, а в v1.1.1 это
исключение перехватывается только общим `except Exception` в конце. Хуже того, при
`builds = []` после ошибки следующий успешный PUT перезапишет файл пустым списком.

**v2:** `ValueError` перехватывается отдельно (считаем файл пустым), перед PUT всегда
используется фактически прочитанное содержимое, добавлены отдельные сообщения для
401/403/404/409.

### F5 🟡 `_show_update_dialog` обращается к несуществующему атрибуту
```python
self.root.wait_window(dlg.top if hasattr(dlg, "top") else dlg)
```

`UpdateDialog` наследуется от `tk.Toplevel` и атрибута `.top` не имеет — условие всегда
уходит в ветку `else`. Работает, но `hasattr`-костыль скрывает ошибку и мешает рефакторингу.

**v2:** `UpdateDialog` — обычный класс с явным `self.top`, как и `CoordinateGrabber`;
ветвлений нет.

### F6 🟡 `restart_app` теряет состояние и не закрывает родительский процесс
`subprocess.Popen([sys.executable, ...])` запускает копию, затем `self.root.destroy()`.
Если программа была запущена через `pythonw` — всё хорошо, но при запуске из консоли
старый процесс может остаться висеть; несохранённые координаты теряются, потому что
`save_config` вызывается только в `on_app_close`.

**v2:** перед перезапуском выставляется флаг остановки автоматизации, конфиг сохраняется,
путь к скрипту берётся из `APP_DIR`, а не из CWD.

### F7 🟡 Формат билда не проверялся при экипировке чужого
`equip_selected_build` брал `b.get("addons", ["—","—"])` и `b.get("perks", [])`, но не
проверял, что навыков ровно 4 и что они не пустые, а сторону не сверял с режимом.

# G. Исправления v2.2.0 (по жалобам пользователей)

### G1 🟠 «Падают только перки, которые есть у всех» (и за выживших, и за маньяков)
Причина была двойная:

1. `OPTION_DEFAULTS["perk_mode"]` был `"general"` — режим «только общие навыки».
   Конфиг пользователя сохранял его, и приложение годами генерировало общие перки,
   хотя выглядело это как баг генератора.
2. Режим `"mixed"` не соответствовал собственному описанию («3 своих + 1 общий»):
   код делал `_pick(unique + common, 4)` по пулу из 3 своих и 13 общих навыков, то есть
   математически ~3.25 слота из 4 занимали общие.

**v2.2:** единая функция `pick_perks(db, side, char, mode, respect_owned)` с честными
стадиями: `mixed` = 3 своих → 1 общий → добить чужими уникальными; `unique` = 3 своих →
1 чужой уникальный → добить общими; `general` = только общие. Дефолт — `mixed`.
`load_config()` один раз мигрирует сохранённый `perk_mode: general` на `mixed`
(флаг `perk_mode_mixed_default_v22` в конфиге; последующий явный выбор не затирается).
`reroll_perks()` использует ту же функцию, поэтому кнопка «Перегенерировать перки»
больше не выезжает за пределы выбранного режима. Тесты: `TestPerkModes`.

### G2 🟠 «Всё белое»: ttk-виджеты вне тёмной темы
`_setup_style()` настраивал только базовые стили (`TLabel`, `TFrame`, `TButton`, …).
У темы `clam` при этом собственные светлые цвета у `Treeview` (весь список билдов
сообщества — белое полотно), `Entry.fieldbackground`, `Progressbar`, `Scrollbar`,
`Panedwindow.Sash` — на тёмном окне это выглядело как белые дыры.

**v2.2:** явно настроены `Treeview` (+ heading + цвета выделения), `TEntry`,
`TCombobox` (+ список), `TSpinbox`, `TProgressbar`, оба `Scrollbar`, `TPanedwindow`/
`Sash`, `TSeparator`, `TMenubutton`, `Toolbutton`; на Windows 10/11 включается тёмная
рамка окна (`DwmSetWindowAttribute`, `DWMWA_USE_IMMERSIVE_DARK_MODE`).

### G3 🟡 Иконки аддонов
В карточке билда иконки были только у навыков. Добавлена карта `ADDON_ICONS`
(768 аддонов из 788 в базе; 15 полностью удалены из игры и отсутствуют в
`Module:Datatable/Loadout` wiki.gg — иконок у них нет нигде, список исключений
зафиксирован в `test_every_addon_has_icon`). Генератор — `tools/resolve_addon_icons.py`:
англ. имя аддона берётся из `Module:Datatable/Loadout`/`Module:Datatable/Icons`,
перевод RU→EN — из сверенной вручную таблицы `tools/addon_names_ru_en.py`, имя файла
проверяется по списку реально залитых на wiki.gg файлов (`IconAddon_x.png` и
`IconAddon x.png` — разные файлы). `IconStore` стал универсальным (`PERK_ICONS` +
`ADDON_ICONS`), кэш общий — `icons_cache/`. В карточке строки аддонов получили
такие же иконки 34×34, как строки навыков; докачка фоновая, заглушка «▢» пока нет файла.

# H. Исправления и новинки v2.3.0

скачиванием и тестом `test_stats_count_perks_and_addons`.

### H2 🟠 Режим «полностью случайные перки»
Добавлен режим `any`: пул = общие + все уникальные стороны, 4 слота без повторов,

### H3 🟡 Конструктор билдов (название, описание, состав)
Новая вкладка «КОНСТРУКТОР»: паспорт билда (title ≤ 60, description ≤ 300),

в `format_build_text`, `build_to_clipboard_text`, карточку и колонку списка.

### H4 🟡 Публикация без токена (kvdb.io)
GitHub Contents API принципиально требует авторизацию на запись, поэтому введён
второй канал: anon-хранилище kvdb.io (корзина владельца, ключ `community_builds`).
`publish_build_anon`: read → `merge_builds` (дедуп по id, новинка сверху) →
PUT → контрольное чтение, до 3 повторов при гонке. Список билдов теперь
объединяет GitHub и облако. Ограничение платформы: запись в корзину открыта
после одноразового подтверждения e-mail владельца — чтение работает всегда.
Тесты: `TestBuildPassport` (payload, формат, слияние, оффлайн-деградация).

### H5 🟡 Дефолтная корзина анонимного канала
С v2.3.1 `ANON_BUCKET_DEFAULT` = корзина, зарегистрированная владельцем на kvdb.io
(`BeFWn1piWxbk42EndgZ7wg`), вместо корзины, созданной скриптом при отладке.
Запись в неё откроется после активации аккаунта письмом от kvdb.io; до этого
`publish_build_anon` возвращает внятную ошибку, а чтение списка работает.

### H6 🟠 kvdb.io заменён на Firebase (v2.4.0)
Выяснилось, что активация аккаунта kvdb.io требует привязку банковской карты —
анонимный канал с таким порогом входа сообществу не подходит. Канал переписан на
Firebase Realtime Database: бесплатно без карты, REST без SDK, запись append-only
(`POST {base}/community_builds.json` с push-ключом), правила
`"$push": {".write": "!data.exists()"}` запрещают правку и удаление чужих записей.
`merge_builds` больше не нужен (нет read-modify-write) и удалён вместе с kvdb-кодом;
конфиги с `backend="anon"` мигрируют на `"firebase"` в `_migrate_options`.

# P. v2.10.1: самовосстановление после обновлений

### P1 🔴 Молчаливая смерть после автообновления на v2.10.0

1. толерантный импорт: `try: import dbd_skins except ImportError: SKINS = None`;

3. `dbd_skins.py` приложен ассетом к релизу v2.10.1: ручное восстановление =
   положить один файл в папку программы.

импортом в первом релизе, иначе старые апдейтеры не смогут их донести.

# S. v2.11.2: русские названия наборов (1568 из 2195) и почему не 100 %

# U. v2.11.4: простыня для ручного заполнения RU-названий

# W. v2.13.0: челенджи (35 ограничений на матч, три уровня сложности)

Задача: в настройках генерации — случайные «челенджи» (например «играй без
палет») с делением на лёгкий/средний/тяжёлый.

### W1 Данные
`CHALLENGES` в `dbd_data.py`: 35 записей `{ru, text, diff, side}`.
`diff` = 1/2/3 (`CHALLENGE_DIFFS` = лёгкий/средний/тяжёлый), `side` =
SURVIVOR / KILLER / ANY (общий «Без аддонов» доступен обеим сторонам).
Распределение: выжившие 7/7/6, убийцы 4/5/5 + 1 общий лёгкий — пул каждой
стороны и сложности не меньше четырёх вариантов (иначе «Другой челендж»
вырождается), что закреплено тестом `test_challenge_data_sane`.

Челенджи придуманы для приложения (в игре такой механики нет), поэтому
формулировки сделаны проверяемыми: указано, что именно запрещено и как трактуется
пограничный случай («ускорение от „Спешки“ считается бегом: если эффект
сработал — стойте, пока он не кончится», «носить фонарик можно, светить — нет»).

### W2 Логика
`pick_challenge(side, diff)` — пул = своя сторона + ANY, фильтр по сложности
(`diff="any"` или 1/2/3). `reroll_challenge(side, diff, avoid)` — то же, но
исключает предыдущее название (если в пуле один вариант, возвращается он же).
Неизвестная сторона -> `None`: иначе ANY-челенджи выпадали бы для любой строки
(на этом поймал тест `pick_challenge("НЕТУ")`).

### W3 Интеграция
- настройка: галка `options.challenge_enabled` (по умолчанию ВЫКЛЮЧЕНА —
  самоограничения не должны появляться без спроса) + `options.challenge_diff`
  (any/easy/medium/hard), обе сохраняются в конфиге;

# X. v2.14.0: челенджи — описания, честные сложности, 45 штук

### X1 🟠 Сложности были расставлены нелогично (отзыв владельца)
«Без бега» лежало в ЛЁГКИХ, хотя выживший без бега не может сделать главное —
убежать от убийцы; при этом «Без палет» (привычка, а не основа выживания) было
средним. «Без силы» у убийцы стояло лёгким, хотя сила — его основная механика.
**Решение:** правило «лёгкий отнимает удобство, средний — одну привычку,
тяжёлый — основной способ выжить/убивать». Переносы: «Без бега» и «Тихий матч»
→ тяжёлые (второй = «без палет» + «без окон» + «без шкафов» разом),
«Без шкафов» → средний, «Без силы» → тяжёлый, «Без палет у убийцы» → средний,
«Без крюков подвала» → лёгкий, у убийцы появился отдельный средний
«Без аддонов у убийцы» (общий лёгкий «Без аддонов» остался).
Раскладка закреплена тестом `test_challenge_difficulties_are_balanced`, включая
кейс из отзыва: `diff("Без бега") > diff("Без палет")`.

### X2 🟡 Челендж был только «условием», без описания
Поле `why` — одна строка «зачем это и в чём вкус» («Убийца быстрее тебя. Всегда.
Сегодня — особенно.»). Показывается в карточке (название → описание → условие),
в журнале и в `build_to_text` отдельной строкой; в компактный текст для чата не
добавляется намеренно — там одна строка на билд. Тест требует `why` ≥ 10 символов
у каждой записи.

### X3 Количество: 35 → 45
Лёгких 10, средних 18, тяжёлых 17; выживших 23, убийц 19, общих 3. Пул каждой
стороны и сложности ≥ 4 (иначе «Другой челендж» вырождается в ту же запись) —
проверяется тестом. Новые механики, которых не было: ограничение по времени на
один генератор («Гость на карте» — не дольше 15 с подряд), запрет бросать

подвал»), запрет переключаться между целями у убийцы («Охота по очереди»),
запрет силы именно в погоне («Без силы в погоне»), запрет любых

запрет мета-сборок («Без сета») и смена персонажа/перков после прошлого матча
(«Без повторений»).
